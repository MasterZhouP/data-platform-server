# 可配置 OA 到 U8 任务设计

## 1. 目标

在不改变 OA 插件“调用平台统一接口”这一边界的前提下，平台新增可配置的 OA 到 U8 推单任务。管理员可在任务页面配置读取 OA 数据的 SQL、U8 业务接口和 JSON 请求模板；OA 插件仅提交稳定的 `taskCode`、`masterId`、`formId`、`summaryId`。

新能力与现有参照任务、定时 U8 到 OA 任务共用任务目录、配置发布、执行日志和运行诊断；它们保留各自适合的执行方式。

首期不开放平台直接更新 OA 或 U8 数据库。凭证号等 U8 结果会被持久化到执行记录，供 OA 插件或人工查询。将来如确认有 OA 业务回填接口，可作为受控后处理器接入；不使用任意 `UPDATE SQL` 作为替代方案。

## 2. 已确认边界

- 平台提供一个统一 OA OpenAPI 受理接口，OA 插件主动调用平台；不新建按任务划分的 OA 对外接口体系。
- `taskCode` 是任务的稳定路由标识，不是流程定义，也不是 OA 表单字段映射。
- U8 token 和账户为共享配置。任务不配置 token 地址、账户、完整主机地址或认证 Header。
- `tradeId`、token 刷新、超时、脱敏、错误标准化由 U8 网关处理，不显示为任务配置步骤。
- OA 到 U8 任务采用单次 U8 业务调用。业务读取可有零到多个顺序执行的命名数据步骤。
- 页面允许填写 SQL 和 JSON 模板，但不允许 Groovy、JavaScript、任意 SQL 写入、流程图编排或自定义网络脚本。
- 外部触发请求只接受已约定的四个上下文字段；SQL 可使用任务常量、前序读取结果和 U8 提取结果，不能因此推导为 SQL 只能使用三项 ID。
- 参照任务保持同步查询；OA 到 U8 保持异步执行；现有 U8 到 OA 销售出库任务维持代码管理，首期不强行改造成配置任务。

## 3. 总体结构

```text
OA 插件
  └─ POST /integration/openapi/v1/executions
       └─ ExecutionAcceptor
            └─ TaskDefinitionResolver
                 ├─ 固定任务修订快照、依赖快照和去重键
                 └─ ExecutorRegistry（按任务类型）
                      ├─ REFERENCE_QUERY：同步参照查询执行器
                      ├─ OA_TO_U8：可配置 OA 到 U8 执行器
                      └─ U8_TO_OA：现有代码任务执行器

OA_TO_U8 执行器
  ├─ 只读 SQL 数据步骤（0..n）
  ├─ JSON 模板渲染
  ├─ 共享 U8 网关：token、tradeId、业务接口调用
  ├─ U8 结果提取与最小化持久化
  └─ 阶段日志、失败分类、断点重试
```

控制面统一，运行时执行器分型。任务目录负责“是什么、当前用哪个版本、是否可运行”；执行器负责“如何运行”。

## 4. 任务与版本模型

新增通用任务目录和不可变修订，而不是为参照、OA 到 U8 分别建设互不兼容的任务管理模型。

### 4.1 `int_integration_task`

稳定字段包括：

- `task_code`、`task_name`；
- `task_type`：`REFERENCE_QUERY`、`OA_TO_U8`、`U8_TO_OA`；
- `enabled`；
- `active_revision_id`、`draft_revision_id`；
- `config_version`；
- 创建、更新和发布审计字段。

代码管理的 U8 到 OA 任务可先登记为 `U8_TO_OA`，但不要求存在可编辑配置修订；任务中心只展示其运行条件和执行情况。

### 4.2 `int_integration_task_revision`

一条修订包含 `task_code`、递增版本号、`DRAFT`/`VALIDATED`/`PUBLISHED`/`ARCHIVED` 状态、`config_json`、校验和、校验摘要、变更说明和审计字段。修订不可修改；编辑总是创建或更新草稿，发布原子切换活动修订。

`config_json` 按 `task_type` 使用受控结构，由后端类型校验器验证。数据源、U8 连接和秘密只保存稳定引用，凭据不进入任务 JSON。

### 4.3 运行快照

受理 OA 请求时解析已发布任务修订，并在执行记录保存：

- `task_revision_id` 和校验和；
- 被引用数据源的活动修订；
- U8 共享连接修订；
- 去重键和触发上下文。

队列等待期间发布新配置不会改变已受理执行的含义。

## 5. OA 到 U8 配置模型

`OA_TO_U8` 修订包含以下区域。

### 5.1 基本信息

任务名称、编码、启用状态、允许的触发来源和非敏感任务常量。任务常量可被 SQL 和 JSON 模板引用，不能保存密码、token 或地址。

### 5.2 数据准备步骤

每个步骤包含：`code`、顺序、只读数据源引用、SQL 正文、命名参数定义、结果基数和输出名。

- SQL 仅允许单条 `SELECT` 或受控的只读查询语句。
- 命名参数通过预编译绑定，禁止字符串拼接和 `${...}` 直接替换。
- 结果基数为 `ONE`、`LIST` 或 `SCALAR`。
- 步骤可使用触发上下文、任务常量和已完成步骤中的标量结果；禁止循环、分支和任意脚本。
- 每个数据步骤在发布前执行 SQL 安全检查、字段检查和样例预览。

变量命名空间为：

```text
trigger.masterId / trigger.formId / trigger.summaryId
task.constants.*
data.<stepCode>.*
u8.response.*
result.*
```

SQL 使用受控的扁平参数别名映射到上述变量，模板和日志展示使用完整命名空间。

### 5.3 U8 业务接口

任务配置业务接口编码或受控相对路径、请求 JSON 模板、成功判断规则、错误消息提取路径和结果输出映射。

第一期默认 `POST application/json`。成功判断和字段提取只支持 JSON Pointer 类路径、HTTP 状态和配置的允许值，不提供表达式语言。发布校验使用脱敏样例上下文渲染模板，检查变量缺失、无效 JSON 和未注册接口。

### 5.4 后处理保留点

首期只持久化任务声明的 `result.*` 输出，例如 U8 凭证编号、凭证内部 ID、外部业务号。配置模型预留有序后处理定义，但执行器不开放数据库更新。

未来若确认 OA 提供回填业务接口，可新增 `OA_API_CALLBACK` 后处理器。后处理必须由已确认 U8 成功的检查点开始执行，不能再次调用 U8 推单接口。

## 6. 统一受理与执行流程

新增统一外部写入入口：

```http
POST /integration/openapi/v1/executions
X-Request-Id: <uuid>
Content-Type: application/json

{
  "taskCode": "OA_EXPENSE_VOUCHER",
  "masterId": "...",
  "formId": "...",
  "summaryId": "..."
}
```

入口只负责请求形状校验、调用方验证、统一响应和关联编号；它内部调用现有 `ExecutionAcceptor`，不另建一套队列或日志体系。响应立即返回 `executionId` 和 `PENDING`，OA 插件通过既有执行详情接口查询最终状态。

受理过程：

1. 校验任务存在、启用、类型可由 OA OpenAPI 触发且全部依赖可用。
2. 获取已发布修订和连接版本快照。
3. 计算固定幂等键。首期 OA 到 U8 默认以 `taskCode + masterId + action` 为同一业务，`force` 仅平台人工操作可用。
4. 创建执行记录和 `RECEIVED` 阶段，发布已有异步执行事件。

运行过程：

1. 加载执行记录中固定的任务修订。
2. 顺序执行只读数据步骤，记录步骤编码、耗时、行数和脱敏摘要。
3. 渲染并保存脱敏后的 U8 请求摘要。
4. 通过共享 U8 网关发送一次业务请求。
5. 确认成功后提取并持久化声明的 `result.*` 输出。
6. 完成执行，或进入将来受控的后处理阶段。

## 7. 执行状态、检查点与重试

在已有 `PENDING`、`RUNNING`、`SUCCESS`、`FAILED`、`SKIPPED`、`RESULT_UNKNOWN` 基础上，新增 `PARTIAL_SUCCESS`。它表示目标 U8 已确认成功，但后续回填或查询动作失败。

新增执行检查点和最小结果输出存储：

- `last_completed_stage`；
- `u8_confirmed`；
- `resume_mode`：`FULL` 或 `POST_PROCESS`；
- `result_outputs_json`：任务声明并允许保留的输出；
- 任务、数据源和 U8 连接的版本快照。

规则如下：

| 失败位置 | 状态 | 重试行为 |
| --- | --- | --- |
| U8 调用前 | `FAILED` 且可重试 | 新执行从数据准备开始 |
| U8 网络超时或不确定响应 | `RESULT_UNKNOWN` | 禁止自动和人工盲目重推；先核对 U8 |
| U8 明确失败 | `FAILED` | 按错误类别决定是否允许完整重试 |
| U8 成功、后处理失败 | `PARTIAL_SUCCESS` | 仅从后处理恢复，不再调用 U8 |

首期没有写库后处理时，`PARTIAL_SUCCESS` 仅作为预留运行语义和后续 OA API 回填的测试覆盖，不要求页面开放配置入口。

## 8. 现有模块调整

| 现有模块 | 调整 |
| --- | --- |
| `IntegrationExecutionService` | 由任务定义解析器校验和固定修订，不再直接要求每个 `taskCode` 都有 Spring Handler。 |
| `PushHandlerRegistry` | 演进为按执行器类型选择；保留代码任务的兼容适配。 |
| `PushPipelineRunner` | 传入修订快照和恢复信息，识别 `PARTIAL_SUCCESS`。 |
| `ReferenceCatalog` / `ReferenceTask` | 迁移到统一任务目录与修订；`sqlResource` 只作迁移输入，不再是生产主路径。 |
| `ReferenceEngine` | 保留参照的分页、筛选和同步语义；抽出底层安全 SQL 执行设施给配置任务复用。 |
| `U8Client` | 演进为共享 U8 网关，实现 token、tradeId、接口调用和统一错误分类。 |
| `ReferenceOpenApiController` | 保留现有参照接口；在同一 `/integration/openapi/v1` 前缀增加统一执行受理入口。 |
| 前端任务页 | 统一任务列表和版本头；参照、OA 到 U8、U8 到 OA 使用类型化页签。 |

## 9. 前端

任务中心负责列表、运行就绪状态、最近执行和类型过滤。每种类型使用独立详情页，复用版本状态栏、数据源状态、SQL 编辑器、JSON 编辑器、预览和执行日志组件。

OA 到 U8 详情页包含：

1. 基本信息；
2. 数据准备；
3. U8 接口；
4. 调试预览；
5. 版本记录。

调试预览默认只执行只读 SQL、展示脱敏数据摘要和渲染后的 JSON；不调用 U8，不移动队列，不写入业务系统。真实 U8 推送只允许通过统一受理接口或受控的管理员测试动作，并保留完整执行审计。

## 10. 安全与运行约束

- SQL 编辑、预览、生产执行全部在后端；浏览器永不获得 JDBC 完整连接信息或密码。
- 读取数据源维持数据库侧只读账户和事务约束。
- U8 账户和 token 不进任务 JSON、执行列表、浏览器存储或普通日志。
- 对外写入接口采用统一的调用方验证策略、`X-Request-Id`、请求体限制和脱敏审计。当前参照接口的临时匿名状态不能原样用于 U8 写入接口；实际认证机制遵循部署的 OA 插件接入策略。
- 任务接口不能配置任意外部主机、Header 或认证信息。
- 执行日志保存版本、阶段、行数、错误码和允许保留的结果输出；大批量原始查询结果和敏感请求响应只保存脱敏、截断摘要。

## 11. 分阶段实施

### 阶段 A：统一任务控制面和参照迁移基础

建立任务目录、修订、发布和运行快照；将参照 SQL 从 classpath 资源迁移为页面编辑、数据库保存和发布执行。保留旧资源作为一次性迁移源和短期回退开关。

### 阶段 B：共享 SQL 与 U8 网关

抽取只读命名 SQL 执行设施；实现共享 U8 token、tradeId、HTTP 调用和错误分类。此阶段不暴露新的 OA 推单接口。

### 阶段 C：可配置 OA 到 U8 执行器和统一受理

实现 `OA_TO_U8` 配置校验、异步执行器、统一 OpenAPI 入口、执行结果输出和重试检查点。前端完成任务配置与只读调试预览。

### 阶段 D：任务工作台、迁移与验收

合并任务列表和执行诊断，迁移一个真实审核推单任务与一个费用凭证推送任务，完成 SQL 预览、U8 沙箱推送、幂等、结果未知和配置版本切换验收。

OA 自动回填属于阶段 D 之后的独立增量：仅在 OA 提供明确业务 API、认证方式和幂等规则后实现 `OA_API_CALLBACK`。

## 12. 验收标准

1. 管理员能在页面创建、校验、预览、发布和停用参照与 OA 到 U8 任务；编辑草稿不会影响活动执行。
2. 参照生产 SQL 不再依赖 SQL 资源文件，运行日志可定位任务、SQL 修订和数据源修订。
3. OA 插件通过一个统一平台接口受理 OA 到 U8 请求，重复请求不会重复创建 U8 单据。
4. 任意数量的配置型 OA 到 U8 任务由同一个执行器处理，不为每个任务新增 Spring Handler。
5. token、tradeId 和账户配置不要求任务重复配置，并且不会泄露到浏览器或日志。
6. 失败前、结果未知、U8成功后失败三类场景具有不同且安全的重试行为。
7. 首期不存在直接写 OA/U8 数据库的接口、SQL 配置或数据源权限。
8. 参照同步查询和现有定时 U8 到 OA 任务功能回归通过。
